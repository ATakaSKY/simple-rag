# Simple RAG with Node.js

A deliberately small RAG application built without LangChain or LlamaIndex.

It demonstrates the core pipeline:

    Documents
      ↓
    Chunking
      ↓
    Gemini embedding model
      ↓
    PostgreSQL + pgvector
      ↓
    Semantic retrieval
      ↓
    Retrieved context
      ↓
    Gemini LLM
      ↓
    Answer

## What each file does

- `ingest.js` — reads documents, chunks them, creates embeddings, and stores them in Postgres.
- `retrieve.js` — embeds a question and asks pgvector for the most similar chunks.
- `ask.js` — combines retrieval with the LLM to produce the final answer.
- `chunk.js` — contains the intentionally simple paragraph-based chunker.
- `gemini.js` — calls the Gemini Embeddings API and `generateContent` for answers.
- `db.js` — creates the PostgreSQL connection pool.
- `schema.sql` — creates the pgvector extension, table, and vector index.
- `documents/` — sample knowledge-base documents.

## Prerequisites

- Node.js 18+
- Docker Desktop (or another Docker runtime)
- A [Gemini API key](https://aistudio.google.com/apikey) (Google AI Studio free tier works)

## 1. Install dependencies

```bash
npm install
```

## 2. Configure the API key

Copy `.env.example` to `.env`:

```bash
cp .env.example .env
```

Then put your Gemini API key in `.env` as `GEMINI_API_KEY`.

Defaults use lightweight free-tier models:

- `GEMINI_CHAT_MODEL=gemini-2.5-flash-lite` — answer generation
- `GEMINI_EMBEDDING_MODEL=gemini-embedding-001` — embeddings (`GEMINI_EMBEDDING_DIMENSIONS=768`, must match `schema.sql`)

You can change either model in `.env` without editing code.

## 3. Start Postgres + pgvector

```bash
npm run db:up
```

Wait a few seconds for Postgres to start.

## 4. Create the vector table

```bash
docker exec -i simple-rag-postgres psql -U postgres -d rag < schema.sql
```

If you previously indexed with OpenAI (`VECTOR(1536)`), drop the old table first:

```bash
docker exec -i simple-rag-postgres psql -U postgres -d rag -c "DROP TABLE IF EXISTS documents;"
docker exec -i simple-rag-postgres psql -U postgres -d rag < schema.sql
```

## 5. Index the documents

```bash
npm run ingest
```

This is the ingestion/indexing phase:

```text
.txt files
   ↓
chunks
   ↓
Gemini embeddings
   ↓
Postgres + pgvector
```

The script truncates the table before ingesting, so it is safe to run repeatedly while experimenting.

## 6. Ask a question

Try:

```bash
npm run ask -- "What filters does Service Map support?"
```

Or start an interactive session:

```bash
npm run ask
```

Then try:

```text
What filters does Service Map support?
How do I enable Service Map in PocketOps?
What can I put inside a dashboard?
How does PocketOps bill for dashboards?
```

The application prints both:

1. The retrieved chunks and their similarity scores.
2. The final answer generated by the LLM.

## 7. Stop the database

```bash
npm run db:down
```

The Docker volume keeps the database data unless you explicitly remove the volume.

## The important architecture

### Indexing

```text
Document
  ↓
Chunk
  ↓
Gemini Embedding Model
  ↓
Vector
  ↓
Postgres / pgvector
```

### Querying

```text
Question
  ↓
Gemini Embedding Model
  ↓
Query Vector
  ↓
pgvector similarity search
  ↓
Top K chunks
  ↓
Build context
  ↓
Gemini LLM
  ↓
Answer
```

The LLM does NOT perform the vector search.

Your Node.js application orchestrates the process, while pgvector performs the vector similarity search.

## A useful experiment

Change the documents in `documents/`, then run:

```bash
npm run ingest
```

and ask new questions.

You can also inspect the database directly:

```bash
docker exec -it simple-rag-postgres psql -U postgres -d rag
```

Then:

```sql
SELECT id, source, content
FROM documents;
```

The actual embeddings are stored in the `embedding` column.

## What this project intentionally does not hide

There is no LangChain, LlamaIndex, or managed RAG abstraction here.

You can see:

- the embedding API call
- the stored vectors
- the retrieval query
- the similarity scores
- the context sent to the LLM

That makes it useful as a learning project before moving to managed retrieval systems.
